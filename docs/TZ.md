# ТЗ: система учета автомобильных запчастей с авторазборки

## Этап 1. Основа приложения и авторизация

Создать адаптивное web-приложение для учета автомобильных запчастей с авторазборки. Основной сценарий — использование с телефона, интерфейс также должен корректно работать на ПК.

### Авторизация

- Вход только по PIN-коду.
- PIN состоит из цифр.
- Каждый пользователь имеет собственный PIN.
- После успешного входа система определяет пользователя и открывает Dashboard.
- Сессия пользователя сохраняется.
- Предусмотреть выход из аккаунта.

### Основная навигация

Фиксированный нижний navigation bar из 4 разделов:

1. Dashboard
2. Сделки
3. Склад
4. Настройки

---

## Этап 2. Dashboard

После авторизации пользователь попадает на главный экран.

В верхней части:

**Вітаємо,  
Богдан Анатолійович**

Справа расположить кнопку **«Вийти»**.

### Балансы

Отображать три типа баланса:

| Счет | Валюта |
|---|---|
| Каса | UAH + USD |
| Крипто | USDT |
| ФОП | UAH |

Пример:

**Каса**
- 125 400 ₴
- $2 350

**Крипто**
- 4 520 USDT

**ФОП**
- 83 200 ₴

Баланс должен рассчитываться системой на основании проведенных финансовых операций, а не быть статическим числом.

Под балансами крупная кнопка:

**+ Створити угоду**

Нажатие открывает экран создания сделки.

### Дополнительная статистика

- Продажи сегодня
- Продажи за месяц
- Количество сделок
- Количество товаров на складе

## Этап 3. Создание сделки

Отдельный экран **«Нова угода»**.

### 3.1. Покупатель

Поле:

**ПІБ покупця**

Обычное текстовое поле.

### 3.2. Получение

Переключатель:

**Самовивіз / Доставка**

Если выбран **Самовивіз** — дополнительные поля не появляются.

Если выбрана **Доставка** — показать одно большое текстовое поле:

**Дані для доставки**

В него можно внести всю информацию в свободном формате:

> Нова Пошта, відділення №15, Київ, +380..., Іван Іванов

### 3.3. Добавление запчастей

Блок:

**Запчастини**

Строка поиска должна искать одновременно по:

- названию;
- каталожному номеру.

Результаты показывать только из существующей базы товаров.

Для каждой позиции отображать:

- Название
- Каталожный номер
- Склад
- Доступное количество
- Цена

После выбора товар добавляется в сделку.

Для добавленной позиции должна быть возможность:

- изменить количество;
- изменить цену продажи конкретно для этой сделки;
- удалить позицию из сделки.

Нельзя продать больше единиц, чем имеется на складах.

### 3.4. Итог сделки

Внизу:

**Загальна сума: 18 500 ₴**

Checkbox:

- [ ] **Кошти отримано**

После активации показать:

**Куди отримано кошти?**

- Каса UAH
- Каса USD
- Крипто USDT
- ФОП UAH

Основная кнопка:

**Відвантажити**

### Сумма и валюта зачисления

После выбора счёта показывать поле **«Сума зарахування»** в валюте этого счёта:

- для счёта в UAH (Каса UAH, ФОП UAH) поле заполняется суммой сделки, но её можно изменить;
- для Каса USD или Крипто USDT поле пустое, и пользователь вводит фактически полученную сумму в $ или USDT (например, сделка на 12 000 ₴, получено $290).

Под полем показывать подсказку:

- для валюты: фактический курс по сделке (`сумма сделки в ₴ / введённая сумма`), например «1 USD = 41,38 ₴»;
- для UAH: если сумма отличается от суммы сделки, предупреждать, на сколько.

Подтвердить зачисление без суммы больше 0 нельзя.

На баланс зачисляется именно введённая сумма в валюте счёта. Сумма сделки в ₴ не меняется.

Та же логика действует в окне **«Отримати оплату»** для уже созданной сделки.

### Логика

- Если **«Кошти отримано» = OFF** → сделка создается со статусом **«Нові»**.
- Если **«Кошти отримано» = ON** → сделка создается со статусом **«Виконані»**, а сумма поступает на выбранный баланс.
- После отгрузки количество проданных товаров автоматически списывается со склада.

## Этап 4. Раздел «Сделки»

Экран должен содержать переключатель:

**Нові | Виконані**

В **«Нові»** находятся неоплаченные сделки.

### Карточка сделки

Пример:

**№000124**  
Іван Петренко  
18 500 ₴  
3 запчастини  
Доставка  
29.09.2026

При открытии сделки показываем:

- ФИО;
- тип получения;
- реквизиты доставки;
- список товаров;
- количество;
- цену каждого товара;
- итоговую стоимость;
- статус оплаты.

Для неоплаченной сделки должна быть кнопка:

**Отримати оплату**

После нажатия пользователь выбирает счет получения денег.

После подтверждения:

- сделка переходит в **«Виконані»**;
- соответствующий баланс увеличивается.

### Поиск

Предусмотреть поиск сделки по:

- номеру;
- ФИО;
- товару.

---

## Этап 5. Склад

Сверху переключатель складов:

**Всі | Склад 1 | Склад 2 | Склад 3...**

По умолчанию открывается **«Всі»**.

Если в настройках какой-либо склад установлен как склад по умолчанию, использовать его при операциях добавления товара. Вкладка просмотра при этом по умолчанию остается **«Всі»**.

### Список товаров

Предусмотреть поиск.

Сортировка по умолчанию — **по алфавиту**.

Карточка товара:

**8K0407253F**  
**Ричаг передній Audi A4 B8**  
2 шт.  
3 500 ₴

Если товара нет в наличии:

- карточка остается в списке;
- становится визуально полупрозрачной;
- отображается `Немає в наявності`.

---

## Этап 6. Карточка запчасти

При нажатии на товар открывается его подробная карточка.

Показывать:

- Название
- Каталожный номер, если указан
- Фото товара
- Цена
- Новая / БУ
- С дефектом / Без дефекта
- Заметка

### Остатки

Например:

**В наявності: 3 шт.**

- Склад 1 — 2 шт.
- Склад 2 — 1 шт.

### Действия

Внизу три кнопки:

**Продати**  
**+ Додати**  
**Редагувати**

#### Продати

Открывает создание сделки с уже добавленной запчастью.

#### Додати

Увеличивает количество товара на складе.

Пользователь выбирает:

- склад;
- количество.

#### Редагувати

Открывает полную форму товара.

## Этап 7. Добавление и редактирование товара

Использовать одну универсальную форму для:

**Новий товар / Редагування товару**

### Поля

**Каталожний номер**

Необязательное поле.

**Назва***

Обязательное поле.

**Наявність**

Возможность указать количество по каждому складу:

- Склад 1 — 3 шт.
- Склад 2 — 1 шт.

**Нотатки**

Свободное текстовое поле.

- [ ] **Є дефект**

Переключатель:

**Новий / БУ**

**Ціна**

**Фото товару**

Разрешить загрузить несколько фотографий товара.

Кнопка:

**Зберегти**

Для существующей позиции предусмотреть:

**Видалити товар**

Использовать soft-delete, чтобы старые сделки не потеряли информацию о проданном товаре.

## Этап 8. Настройки — пользователи

Путь:

`Настройки → Пользователи`

Список пользователей.

Пример:

**Богдан Анатолійович**  
PIN: ••••

Действия:

- добавить;
- редактировать;
- удалить/деактивировать.

### Форма пользователя

- **Ім'я**
- **PIN-код**

PIN-коды разных активных пользователей не должны совпадать.

PIN желательно хранить в базе не открытым текстом, а в виде hash.

---

## Этап 9. Настройки — склады

Путь:

`Настройки → Склады`

Пример списка:

- **Склад 1** ⭐
- **Склад 2**
- **Склад 3**

Можно:

- создать склад;
- переименовать;
- деактивировать.

### Форма

**Назва складу**

- [ ] **Склад за замовчуванням**

Одновременно складом по умолчанию может быть только **один склад**.

Удалять склад, на котором числятся товары, нельзя. Сначала товар необходимо переместить либо обнулить остатки.

---

## Этап 10. Архитектура остатков

Не хранить просто поле `quantity` внутри товара.

Использовать отдельные сущности:

- `Products` — сами запчасти;
- `Warehouses` — склады;
- `Inventory` — остаток конкретного товара на конкретном складе.

Пример:

| Product | Warehouse | Quantity |
|---|---|---:|
| Ричаг Audi | Склад 1 | 2 |
| Ричаг Audi | Склад 2 | 3 |

Во вкладке **«Всі»** показывается:

**Ричаг Audi — 5 шт.**

Внутри карточки:

- Склад 1 — 2
- Склад 2 — 3

Архитектура должна позволять в дальнейшем реализовать перемещения между складами.

---

## Этап 11. Движение товара

Каждое изменение остатка записывать в историю.

### Типы операций

- Приход
- Продажа
- Корректировка
- Перемещение между складами
- Возврат

Пример:

> **29.09.2026 16:42**  
> Продажа  
> Ричаг Audi A4 B8  
> Склад 1  
> −1 шт.  
> Сделка №124  
> Богдан Анатолійович

Изменение остатка не должно происходить бесследно.

Для каждой операции необходимо сохранять:

- кто сделал изменение;
- когда;
- какой товар;
- какой склад;
- старое/новое количество либо изменение количества;
- причину/тип операции;
- связанную сделку, если она есть.

---

## Этап 12. Финансовые операции

Балансы также должны иметь историю операций.

Не изменять баланс просто числом.

Создать журнал финансовых операций.

Пример:

> Продажа №124  
> +18 500 ₴  
> Каса  
> 29.09.2026

Это должно позволить в дальнейшем добавить:

- расходы;
- переводы между Касса / ФОП / Crypto;
- возвраты;
- корректировки;
- отчетность.

Dashboard получает текущий баланс как результат финансовых операций.

## Этап 14. Порядок разработки для Claude

Не реализовывать всю систему одним большим изменением.

Разрабатывать последовательно:

```text
1. UI shell + PIN-авторизация
↓
2. Dashboard
↓
3. Products + Warehouses
↓
4. Inventory
↓
5. Добавление / редактирование товара
↓
6. Создание сделки
↓
7. Раздел сделок
↓
8. Inventory Transactions
↓
9. Финансы и балансы
↓
10. Settings
↓
11. Финальное тестирование
```

После каждого этапа:

1. Проверить реализованный функционал.
2. Не переписывать уже работающие экраны без необходимости.
3. Сохранять существующую архитектуру.
4. Проверять существующие функции на регрессии.
5. Только после проверки переходить к следующему этапу.

## Важное требование для авторазборки

Архитектуру необходимо проектировать так, чтобы в будущем каждая физическая запчасть могла иметь **уникальный ID**, даже если у нескольких деталей одинаковый каталожный номер.

Например:

Две одинаковые фары с одним каталожным номером:

- Фара №1 — БУ, без дефектов — 8 000 ₴
- Фара №2 — БУ, трещина корпуса — 5 000 ₴

Это позволит отдельно хранить для каждой физической детали:

- состояние;
- дефекты;
- фотографии;
- цену;
- склад;
- историю перемещений;
- историю продажи.

При этом одинаковые детали могут объединяться в интерфейсе поиска по каталожному номеру или названию.
